随后第二次进入 DFU，只读导出 `after_controls/`，发现：

- 应用整区与获批 v2 加 FF 相同，整区 SHA 为
  `2976a7578fe4af7e27fcb0f424be0a8d5771b8163f557ab81e881d605b42242d`。

  `04614802a0f2930334e0ff48b231a497c4e306700cbda86ca014325d77f630c7`。
  差异地址为 `0x7F420..0x7F423` 和 `0x7F440..0x7F47F`；逐字节清单在 `audit.json` 的
  `config_differences`。主机没有向配置页发出擦除或下载请求。

【观察】配置保存采用 32 字节追加记录。刷前有效记录在 `0x7F420`；回读时其 magic 被清零，
`0x7F440` 多出一条已失效记录，`0x7F460` 是新的有效记录。
中间记录相对于原有效记录仅配置 key `0x11` 从 `03` 变成 `02`，最后又回到 `03`；
最后有效记录的 28 字节载荷与刷前有效记录完全相同。**用户设置最终载荷相同不等于未写闪存。**

【观察】原厂 `0x3370C` 会比较 RAM 的 `0x2000466D` 与配置 key `0x11`，不同时调用
`0x179D8(...,0x11,2)`；后者经 `0x1788C`、`0x178B4` 保存。
`0x33FA4` 也可保存该字段；`0x3401C`/原页面加载会经过 `0x3370C`。
【推断】此次差异与原厂 GUI 维护状态时保存该字段相容；尚无设备侧调用轨迹证明具体触发源。
【未知】key `0x11` 在本次状态变化中的完整业务含义，以及写入发生在 60 s 启动空跑、20 次循环，
还是再次进入 DFU 前后。两次 dump 把这些阶段包含在同一观测窗口内，不能直接宣称
“已证明 ENTER/LEAVE 本体写配置”，也不能忽略失败继续称其“不写闪存”。
