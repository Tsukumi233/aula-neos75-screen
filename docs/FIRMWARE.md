## 证据和构建

- 【观察】输入 app 区 `0x8000..0x7EFFF`，长度 `0x77000`，SHA-256 为
  `66679ff2cb06ab5a5e47673f679e14e68bf2082fb6401b3808ca58d7f2e1a40c`。
  有效内容及原 DFU suffix 到 `0x4AACC`（不含），后面全 FF。新代码位于 `0x4AB00` 起的空区。
- 【观察】编译器为 developer.arm.com 的 Arm GNU Toolchain 14.3.Rel1，GCC 14.3.1 20250623；
  `-mcpu=cortex-m3 -mthumb -Os -ffreestanding -nostdlib`，仅生成目标支持的 Thumb-2 子集。
  无 C 库、无运行时加载器、无浮点库、无时间戳/build-id。Python 依赖见 `firmware/requirements.txt`。
- 【观察】生成器先校验完整 SHA-256，再独立校验每个改写点原字节；使用显式异常，Python `-O`
  也不能绕过。只改表中钩子及追加区域，向量表和原有地址均保留。
- 【观察】原始引用主要来自 `firmware/analysis/decompiled.c`，Ghidra 未识别的一些任务入口已用
  Capstone 对原机器码和任务表重新核对。云端地址未用于打补丁。
- 【观察】v2 尝试 REA 工具发现本机 Ghidra 提供器未配置，未改设置或启动目标；继续用现有
  反编译、Capstone 与 Unicorn。可复现导出见 `firmware/analyze_canvas.py` 和
  `firmware/analysis/canvas_v2.txt`，包含资源容量、缓存清除及 JPEG 寄存器配置的原字节。
- 【观察】首批依赖安装继承了本机 pip 配置，日志列出了 USTC/PyPI 双索引，因此不能证明首批
  下载仅使用 pypi.org；这是本次执行的网络约束偏差。后续安装已使用 `--isolated --index-url
  https://pypi.org/simple --no-cache-dir`。编译器从上述官方 Arm 地址下载，未使用第三方编译器。

所有原函数地址均写偶数 VA；函数指针和 trampoline 的间接跳转地址置 Thumb bit。遵守 AAPCS：
r0–r3 为参数及易失寄存器，r4–r11/SP 保持，返回用 r0；八字节栈对齐由编译器维护。每个入口
trampoline 重放恰好四字节原序言，再加载带 Thumb bit 的原入口+4，不依赖新旧 PC 差值。
【观察】原向量中的初始 MSP 为 `0x2000C548`，补丁不改变该值或任何原任务栈地址。

此结论依赖该镜像中没有未识别的间接写入，仍需硬件回归。

【观察】原厂 320×320 图的绝对起点为 `(140,20)`，覆盖 x=140..459、y=20..339，左右边距不对称。

### v2 输出区容量、归还及 stride 证据

【观察】装机构建 `0x3230C` 的资源成功路径直接调用
`0x1CB88(0x800D4200,length,NULL,0x800FE604,0x7E900,1)`。固定池容量 518400 字节，
大于整屏 RGB565 的 345600；补丁最多使用前 `0x54600` 字节，不需要证明 GUI 堆还能分配一整屏。
池末 `0x8017CF04` 与原堆底 `0x8017CF08` 相隔 4 字节；原池头在像素地址前 4 字节，输入区也不重叠。
GUI 堆仍仅扣除原 v1 的 Runtime 0x1200，静态/动图原分配 0x32008 未缩小，原有地址未移动。
【推断】基于该池原用途、共享输入三入口保护和单 GUI 任务串行执行，实时期间可独占；未识别的间接访问
仍列为硬件回归风险，不能仅凭“容量足够”认定安全。

【观察】`0x0CA94` 命中缓存后会复用打开记录，`0x191E8` 的资源文件句柄可继续读旧 RGB 地址。
因此 v2 在 LEAVE 中按顺序：隐藏实时 image → `0x23FA0(NULL)` 关闭并清空 LVGL 图像缓存 →
`0x235D4()` 清资源 cookie → 清 `0x2000BD94` → DMB → active=0 → 直接加载保存 screen、invalidate。
不能等加载完 screen 才撤销 guard，否则同步绘制资源会被自身 guard 拦截。
【推断】下一次原页面绘制必须重新打开资源；cookie 不匹配使 `0x3230C` 重读并解码同名 JPEG，恢复借用池。
静态/动图 RGB 未被动过，可直接恢复显示；不再调用含配置保存的静态加载器。原始缓存关闭/清零和
同名资源重新解码分支已在 Unicorn 执行原备份机器码验证，外闪读取和硬件解码均为明确桩。

【观察】`0x9450` 写寄存器 `0x4000B010=(H-1)<<16 | (W-1)`，RGB565 输出地址写
`0x4000B01C`。`0x9570→0x958E→0x9624` 从解析 W 经 double 0.5（常量 `0x98C0`）计算
并写 `0x4000B014`；输出配置只提供格式和基址，没有独立 stride 参数。
【推断】该字段是以 32 位字为单位的输出行跨度，偶数 W 时为 W/2；原接口产生紧密 W×H RGB565。
【未知】硬件是否允许在启动前覆写该字段得到任意 stride，缺少芯片寄存器规格及实测，不做这种覆写。
v2 让描述符/对象匹配 W×H，解到池首，故无需在小帧解码时写 480 行跨度，也无需整屏暂存和逐行搬运。

## 接收、状态机与线程安全

HID 两个钩子只分类、复制一份完整 64 字节报告及更新队列标志。BA 的来源仅允许 HID `0x0C`；
串口不成为第二个生产者。A5 3B 在 USB 11/13 类解析入口被消费，避免先转发到 UART 后产生第二个生产者。
新 BA 不进入原首包、块提交、收尾、外闪写、上传进度或 3 s 恢复代码。

【观察】Runtime 的 `head/tail` 是单生产者/单消费者 u32 计数；32 个报告槽。生产者先拷贝、DMB、
发布 head；GUI 完整读完槽后 DMB、发布 tail。对齐 u32 访问在单核 Cortex-M 上为单次访问。
只有 HID 写 head，只有 GUI 写 tail；GUI 是状态机、统计、描述符及 TX 队列的唯一写者。
active/route/overflow 为有界通知，不执行 LVGL、解码或分配。新增 host_tick 是对齐 u32 的最后主机活动时间，
HID 收到实时包时更新，GUI 控制处理也更新；两者使用同一只读 tick 源，不使串口成为报告队列生产者。

GUI 每次最多处理 16 报告，TX 队列保留两槽余量，每周期最多发一个 64 字节报告。
溢出时中止当前帧、丢弃排队报告、发 status 04；不会把余下数据交回原厂上传器。
一旦见过实时首包，route 保持实时直到明确收到模式关闭状态下的原厂 B0/FC 首包，因此 LEAVE
后的实时残包也不会触发外闪写。

状态为 0=空闲、1=接收、2=READY、3=分块拷 RGB。STATUS 对外 state 为 off=0，active 时为内部值+1。
GUI 校验包长、4096 字节边界与 zlib CRC；首包 ACK 和每满块 ACK 均在 GUI 构造，尾块没有 CRC/ACK。
BA 数据包的 `n` **只计算数据字节**，完整块最后一包的 CRC32 小端值位于 `p[2+n:6+n]`，
不计入 `n`。标准分包为每块 66 包 `n=62`，再一包 `n=4` 加 4 字节 CRC；接收计数和 CRC 累计
均只覆盖数据。允许块中间 `1..61` 字节短包，不强制每包 62 字节；不允许跨块或超出流长。
块末包含 CRC 的报告仍须≤64 字节，因此该包 `n≤58`，否则返回 03 而不越界读 CRC。
READY 后校验类型、帧数=1、delay=0、非零偶数 W≤480/H≤360、长度≤输入区，以及 RGB 精确长度或 JPEG 长度。
错误不会进入解码：结构/大小/CRC 错误 status 03，JPEG 格式/硬件完成失败 status 02。
未进入模式 status 05，忙 status 04。取消在途帧的 LEAVE 发送 status 05 后再回复控制结果。

JPEG 预检拒绝 progressive、非 8-bit、非三分量及非 4:4:4/4:2:2/4:2:0；有界扫描所有段，检查
DQT 非零量化值、DHT 长度/码树/符号、SOF/SOS 参数及 EOI/转义/重启标记。仅允许 APP0 JFIF 与 COM，
拒绝其余 APPn。当前支持常见的分量 ID 1/2/3、量化/Huffman 表 0/1 及单 scan；更宽泛的合法 baseline
编码可能返回 02，见未验证事项。预检后将 JPEG 前移到 scratch 对齐地址，保持原厂 DMA 源对齐习惯。
DMA 启动前和发布最终图像描述符前执行 DMB；这不替代真实外 RAM/DMA 可见性测试。

【观察】JPEG 始终在 GUI 调原 `0x1CB88`，显式给容量 345600、同步参数 1；调用后额外检查 ISR 完成字节。
有效帧开始改写 RGB 前隐藏 image 并清图像缓存，避免缓存沿用旧描述符的宽高；RGB 每次最多复制
4096 字节，直到完成才更新持久 descriptor、尺寸、居中位置，撤销隐藏并 invalidate。
解码失败保持隐藏，避免显示半帧；下一有效帧可恢复。错误流头尚未改写像素时保留上一张完整图。
新会话 ENTER 也隐藏旧 image，避免上次 descriptor 指向原厂重新生成的资源像素。
frame-done 在 GUI 构造和发送。
序号 u16 回绕，frames_ok/err u32；decode_ms 含 RGB 分片所跨越的时间，饱和到 65535。

ENTER 保存当前 screen、选择固定资源 RGB 池、加载独立实时 screen。LEAVE 的缓存归还顺序见上文。
ENTER/LEAVE 没有走 `0x3C068`、原页号保存或含保存的静态重载，也没有主动调用外闪擦写。
v3 在实时可见时仍调用原 `0x33FA4(0)`，只为保留先前用户选择原厂页产生的合法延迟保存，详见旋钮一节。
【推断】GUI 串行执行且所有池使用者受到保护时，隐藏对象期间 GUI 不会从正在改写的池读取像素；
RGB 多周期拷贝期间可以显示黑底，完成后才绘制整帧，避免 LVGL 逐片读取造成的混帧。
硬件 scan-out/加速器是否在 GUI 回调外持有源池仍需 v2 实测；DMB 和隐藏不构成物理垂直同步保证。
本实现不宣称屏幕扫描级原子换帧，frame-done 也不代表面板已完成扫描。

## 配置写入触发源与 v2 离线修复

### 真实原厂代码观察

【观察】`firmware/tests/stock_gui.py` 不使用原简化模拟器中的 GUI/页面/配置返回桩，而是执行：
原 scatter-load 七个区的复制/解压/清零、RAM 中的内存函数、原 GUI 初始化/堆分配、原页面创建与加载、
LVGL 图像缓存打开/关闭/失效、文件驱动、JPEG 参数解析及寄存器配置、原 GUI timer handler `0x2C648`、
页面周期回调 `0x3423C`、状态更新 `0x3401C/0x3370C` 和配置保存逻辑。
v1 和失败 v2 用留存的原 bin/JSON 只读加载并核对 SHA，不重建历史版本。

【观察】稳定输入下，60 s 虚拟时间（6000 次 10 ms 页面回调，另调用实际 timer handler）、20 次
ENTER/LEAVE 和三帧 RGB，都不改变 `0x2000466D/E`，也没有进入列出的存储链。
**没有发现 v2 的 ENTER/LEAVE 自行把 RAM 的 03 改成 02。** 实际记录到的状态写入来自原 A5 35：

【观察】在实时模式内喂入有效 A5 35，将状态从 03 改成 02，随后从实际补丁 LEAVE 入口运行，

### 修复范围和不会延迟补写的依据

只新增一个原指令改写：`0x3379C` 的 `E4 F7 1C F9`（BL `0x179D8`）改调 `rt_status_save`。
它仅在 `restoring==2` 且 `(data,key,size)==(0x2000466D,0x11,2)` 时返回；其余情况原样转调完整
`0x179D8`。没有改动 `0x179D8`、`0x17A1C`、`0x17A4C`、`0x1788C/0x178B4` 或底层 flash 入口。

窗口顺序为：LEAVE 置 restoring=2 → 隐藏 image/归还资源缓存 → 撤销 active → 加载保存的 screen →
在同一次 GUI 调用尾部真实执行一次 stock_poll → 清 restoring=0。新 ENTER 清除旧窗口状态，
包括同一队列批次内 LEAVE/ENTER 连续到达的情况。该标志只由 GUI 任务写，HID 仍只入队。

原 `0x3370C` 继续完成样式、百分比文字和最后显示缓存的更新；**不回滚 `0x2000466D/E` 的有效实时输入**，
也不把假值写入配置缓存来躲过比较。下一轮中，显示缓存等于当前实时状态，非强制刷新会直接返回，
不延迟补调保存；随后状态回到原存储的 03 时，虽然刷新画面，但 key 0x11 比较相等，也不会保存。
新增真实代码回归在窗口结束后继续运行 timer 并再次更新为 03，验证整个过程存储链调用为 0。

原 v1 的静态重载配置保护仍只认 restoring=1；新状态窗口值 2 不扩大旧 `0x11AB2` 的抑制范围。
直接执行 `0x17A1C` 的亮度设置、`0x17A4C` 的页号设置和 `0x33FA4(1)` 的显式保存时，即使人为将
restoring 保持为 2，真实保存逻辑及模拟的 NOR 编程仍执行，证明没有全局屏蔽、清 dirty 或丢掉用户设置。

修复只处理 RT 恢复附带的自动状态持久化。**首次 ENTER 之前的原厂启动、恢复窗口以外收到的新状态或
用户明确发出的原厂设置/保存，保持原行为**。若要把“任意原厂正常输入永不写配置”也作为要求，就会与保留
原厂合法保存冲突；本构建不作这种全局改变。上机启动窗口若另有独立保存，仍需按时间进一步隔离确认。

随后 20 次循环中前两次在实时模式内分别注入 02、03，夹入三帧 RGB，再运行实际 timer handler。
`--captured-config FILE --expected-config FILE` 可选；未传时用可提交的合成配置记录，测试不依赖私有 dump。
留存产物分别位于 `firmware/build/v1/`、`v2_failed/`、`v2_configfix/`；`--baseline v2` 指向
留存的配置修复，保留旧命令的可复现性；`--baseline v3` 则使用当前目录的旋钮构建。

完整日志 `firmware/build/config_trace_*_telemetry.json` 包括每个被监视 RAM 写入的 PC/LR/SP、写前值、
新值，以及每个保存链入口的参数和实际 BL/BLX 调用栈；监视实时状态、GUI 显示缓存、配置 RAM、dirty、
页号待保存计时。调用栈记录显式调用和调用者 LR，不冒充 ISR/RTOS 调度跟踪。
对历史输入，v1/失败 v2 用上机 `after_controls/` 作预期；修复 v2 用原 `pre/` 作预期，均要求整页一致。

明确建模的边界：HID FIFO 发送 `0x32034`、日志 `0x11DBC`、DMA 初始化 `0x2307C`、JPEG 信号量
等待 `0x30EE4`（按已真实配置的 JPEG 寄存器完成输出）、NOR 解锁/锁定/擦除/编程
`0x8FD0/0x8FB0/0x8F68/0x090E8`。原 DMA RAM 包装继续执行，通过内存寄存器模型完成填充/复制。
模拟 NOR 校验范围和 1→0 编程；没有访问任何物理设备。

原厂外部资源未采集，使用合成的 480×360 baseline JPEG 和 320×320 持久图代替；真实文件查找、软件
JPEG 信息解析、硬件解码包装、LVGL 缓存及静态图恢复仍执行。虚拟面板裁剪到 64×48 以减少无关的 CPU
像素混合，应用仍用其原 480×360 页面布局；这证明配置路径，不验证完整屏幕渲染或原 NOR 内容。
Unicorn 用带 FPU 的 Cortex-M7 指令模型执行原厂浮点代码，不声称准确模拟 UB32 的时间、缓存和中断。

## v3 旋钮兼容：原厂路径、槽位与持久化

### 消息入口和 GUI 上下文证据

【观察】以下来自装机构建反编译、原字节及真实机器码模拟；没有读取物理串口、GPIO 或 USB。
补充静态笔记为 `firmware/analysis/knob_paths.md`，模拟入口为 `firmware/tests/stock_gui.py`。

| 地址 | 功能 / 调用约定 | 证据与任务上下文 |
|---|---|---|
| `0x3E8B8` / `0x3EA70` / `0x3EA9C` | vTask_Uart / 取环形缓冲 / BL `0x103BC` | UART 消息通过订阅队列分发；负载在消息 `+0x26`、长度 `+0x24`，不在此处调用 LVGL |
| `0x103BC` / `0xEAA8` / `0xEBFA` | 消息分发 / app_control 任务 / BL `0x35094` | app_control 表项 `0x45D7C`，入口指针 `0xEAA9`；原 A5 包由此进入 `0x35220` 分发 |
| `0x433EE` / `0x1CD4C` | A5 39 按键映射表 / 原 producer | `39 01→(type=2,value=0)`，`39 02→(1,0)`；r0=type、r1=value，消息为 `(type<<16)|value` |
| `0x1CCE8` / `0x2000BCFC` / `0x45D20` | key queue 初始化 / 句柄 / 配置 | 原队列 20 条、每条 4 字节；满时 producer 丢最旧一条再放新条。保持原代码 |

真实 producer → consumer → `0x1D184` → 新包装器 → 原页面代码的模拟中覆盖。
串口、app_control、GPIO 扫描和 HID 都没有新增 LVGL/切页动作；GUI 按键回调和页面 timer 在同一任务中串行。

【未知】镜像包含 GPIO 编码器实现，但未找到 `0x17CA8` poll wrapper 的调用/函数指针或 MOVW 地址引用，
不能证明该实现实际启用。因此能证明 UART A5 39 和 GPIO 方向消息的代码路径，不能证明物理旋钮当时走哪条链，
也不能把 next/previous 的代码映射冒充实测的顺/逆时针方向。

### 六页顺序、门禁与按下

【观察】原表 `0x44848` 共六项，每项 `{root_global,create,load}`，长度 12 字节。下表函数为偶地址：

| 页号 | 根指针全局 | create | load | 已确认内容 |
|---:|---|---|---|---|
| 0 | `0x200034AC` | `0x35918` | `0x117D8` | page1_bg、page1_dg 动态资源 |
| 1 | `0x200034DC` | `0x3600C` | `0x11848` | page2_bg、按键文字 |
| 2 | `0x20003510` | `0x367EC` | `0x11894` | page3_bg、计时文字 |
| 3 | `0x20003544` | `0x37170` | `0x118D0` | page4_bg、动画初始化 `0x314C0` |
| 4 | `0x20003568` | `0x376D0` | `0x11914` | 原持久静态图；无效资源时隐藏图像，仍保留该页 |
| 5 | `0x20003580` | `0x379AC` | `0x11ABC` | page6_bg、page6_dg 动态资源 |

原 next 为 `(current+1)%6`，previous 为 `(current+5)%6`，无资源可用性跳页分支。
新武装循环为 **`0→1→2→3→4→5→RT→0`**，反向完全反转；未武装时直接执行原 `0x1D094`，跳过 RT。

【观察】门禁有两层，不能简化为“BF77 为零就锁定”：原 key 首部仅在
`BF77==0 && *(u32*)0x2000349C!=0` 时返回；原 page 接受条件为
`(BF77&1)!=0 || context==0`，且 overlay byte `0x200044AE==0`。
overlay 非零时，原 key 仍可能先改 current byte `0x200044AD`，但原 page 不切换。
包装器在不允许切页时完整调用原 key，保留这种 RAM 更新，不创建槽位或绕过门禁。

【观察】`A5 39 03` 可产生 `(3,0)→key 0A`，`(0,0)` 也映射 `0A`；`A5 39 A0` 可产生
`(9,0)→key 53→0x3C068(0,0)` 返回临时页。它们均不是物理旋钮 press 已被确认的证据。
【推断】`0A` 可能是通用确认键。**【未知】物理按下是否发到屏幕、使用哪种原始消息仍未知；
当前不凭空把 `0A` 或 `53` 报成 `21 00`，其原厂行为完整保留。** 没有修改协议中“确认可达才报告按下”的条件。

【上机 2026-11-07】按下旋钮时电脑打开了“计算器”，屏幕端没有任何事件：按下由键盘 MCU 作为它自己的按键
（默认 Calculator 媒体键）直接发给电脑，不经过屏幕芯片。因此协议的 `21 00` 不可实现，固件不报告按下。

### 钩子、状态和事件

新钩子是 `0x1D268` 的完整 BL，原字节 `FF F7 14 FF`，重定向 `rt_key`，最终新字节见构建表。
不修改 `0x1D094` 首四字节：`80 B5` 后接四字节 MOVW，取四字节做 trampoline 会截断指令。
`rt_key(uint32_t code)` 遵守 AAPCS，返回 void；只由原 GUI read callback 调用。

- `active` 保留其原布局与含义，等于协议 `visible`；新增 `armed`，区分会话有效和画面可见。
  `previous`/`previous_page` 保存最近一次进入槽位前的原厂 screen 与页号；`discard` 标记隐藏流。
  Runtime 大小 `0x10A0`，仍在原 `0x1200` 保留区内；每字段地址见构建表。
- ENTER 成功后武装并显示；从 stock 页转回槽位会重新隐藏 image、加载不透明黑根，直到新帧完成。
  重复 ENTER 不覆盖入口页；已经可见时不重复发“可见性变化”。
- 可见时 next 先归还资源，令 current=5，再执行原 key 选择页 0；previous 令 current=0，再原 key 选择页 5。
  原厂页之间仍走原 key/page。槽位本身没有可保存的页号，任何时候都不把 6 写入原 current 或 pending。
- LEAVE 解除武装；可见时回最近一次进入 RT 前的 stock 页。隐藏时 LEAVE 只解除武装，保留用户用旋钮选中的
  当前 stock 页（与隐藏超时一致），不发可见性变化。
  超时隐藏时只解除武装、保留当前 stock 页；超时可见时归还资源并恢复入口页。
- `host_tick` 在收到 A5 3B 或已路由的 BA 实时包时刷新；10000 ms 无主机活动后由 GUI 解除。
  **旋钮不是主机活动，不续租**；32 位无符号 tick 差允许计时环绕。超时不重启、不写配置。
- GUI 私有 TX 环构造 `20 visible reason` 和 `21 dir`；武装时每个已识别方向均发 `21 01/FF`，
  即使原厂门禁阻止切页也报告转动。只有 visible 变化才发 `20`；reason=1/2/3 分别为旋钮/主机/超时。
  HELLO 新 timeout 位于报告 bytes26..27，STATUS 的 visible/armed 位于 bytes18/19；报文 checksum 保持原规则。

【观察】隐藏但武装时，对格式正确的 BA 流只计长/CRC，不读写输入区、RGB 池或 descriptor；
保持首包和满块 ACK，收完发 frame-done `05`。这避免真实 SDK 在隐藏竞态中等待 ACK 超时。
未武装首包保持立即 `05` 的旧行为。
【上机 2026-11-07】快速来回拧时，隐藏中开始的丢弃流尚未收完，旋钮又转回槽位：`e8b66862…`（第一版 v3）的 `enter()` 直接清零状态，余下包被静默忽略，主机等 ACK 超时。修正后 `enter()` 遇到进行中的流先发 `05` 再清零（`397675a3…`），SDK 同时在 ACK 超时且期间可见性变化时按“隐藏”处理，兼容已刷入的第一版。回归见 `tests/integration/test_knob.py`。共享缓冲逐字节不变同时在 native GUI 模拟及真实 SDK 集成测试中核验。
原厂页面自己的正常重解码仍可使用共享池，测试将它与“收到隐藏帧导致的写入”分开。

### 动画定时器泄漏（上机发现，已修）

【上机 2026-11-07】多次经旋钮进出实时槽位后，原厂动图越来越快。【观察】原 `0x3C128` 只在“当前活动 screen
就是该页 root”时调用停止函数（页 0 `0x33F64`、页 3 `0x33F80`、页 5 `0x33F88`）；而页 0/5 的加载函数
`0x117D8/0x11ABC` 先经 `0x3F3B4` 把定时器句柄清零（不删除），再由 `0x3F444` 新建 lv_timer。离开槽位时活动
screen 是我们的，原停止条件不成立，旧定时器成了孤儿，每次往返多一个（步进同一动画结构，加速并泄漏 LVGL 内存）。
修复：`rt_key` 离开可见槽位时，按 `rt.previous` 套用原 `0x3C128` 的三条停止条件，再交给原 key/page 加载目标页。
回归 `test_slot_round_trips_do_not_leak_stock_animation_timers` 等在真实原厂代码中逐页数 `0x3F4A0` 回调的定时器数，
与纯原厂参考一致；去掉修复时每页约 19–20 个。【观察】原厂自身在首次创建页 0 时也会留下 1 个孤儿定时器
（create 路径也调用加载函数），之后恒定不增长，作为基线保留不改。修复后 dev `c7d2a4c1…`。

### 输入队列溢出时的过期事件（上机发现，已修）

【上机 2026-11-07，c7d2a4c1】极快地转旋钮时，原厂换页让 GUI 任务停顿，32 条输入环溢出。旧逻辑无论有无流都 `fail(4)`，
这个“没有对应流”的 04 恰好在主机下一次起始包之后到达，SDK 把它当作新帧的结果而停止上传；设备其实已接受新流，
停在“接收中”，直到下次转动。修复：溢出只在正在接收（state 1）时报 04；接收中又收到新起始包时视为主机放弃旧流，
静默替换（只计错误数，不发事件），解码中（state 2/3）仍报 04。由此主机在起始包之后收到的 frame-done 都属于该起始包。
SDK 另外在起始包 ACK 之前收到 frame-done 时短暂等待 ACK（兼容 c7d2a4c1），并对超时的实时请求重试一次。
修复后 dev `cba6f2c7…`。

### 主机分页（两个版本）

### 区域帧（两个版本）

`5A` 流数据以 `UR` 开头时为区域帧（w、h、x、y、jpeg_len，14 字节头）。`validate_region` 要求 w、h 为 16 的倍数、
x、y 为偶数、在 480×360 内、`w*h*2 <= 172800`，且 `rt.canvas`（已显示整屏 480×360 帧）为真，否则 03/06。
`display_region` 把 JPEG 对齐复制到 RX 起点，解码到借用池尾部 `0x80152C04..0x8017CF04`（不越出原池），
按 32 位逐行复制进整屏帧，再调原 `lv_obj_invalidate_area`（`0x295A4`，int16 x1 y1 x2 y2，经反编译确认
与 `0x29558` 相同的调用方式）只重绘该矩形；不隐藏对象、不改描述符。整屏帧开始解码前、`hide()`、`enter()`
清 `rt.canvas`。HELLO flags bit3（dev 15，release 14）。回归：精确矩形逐字比对、无画布 06、几何校验 8 组、
最大区域只用池尾、解码失败保留画布。构建 dev `1d4c029f…`、release `ed903087…`。

### 流畅性：5 ms 节拍、流水线起始包、页缓存（两个版本）

- 【观察】GUI 任务 `0x3C5F8` 循环：`lv_timer_handler 0x2C648` 后 `osDelay(5)`；钩子所在定时器由 `0x2C574(cb,10,0)`
  创建，`lv_timer_t.period` 在偏移 0。`rt_gui` 在槽位显示时写 5、否则写 10（空指针跳过）。LVGL 刷新定时器为 15 ms。
- `rt_gui` 输入循环：遇到 BA 起始包而上一帧 state 2 时先 `display()`；state 3（RGB 分拍复制）则保留起始包到下一拍。
- 页缓存：池尾 `REGION_RGB+81920 .. 0x8017CF04`（90880 字节）按页数均分槽位；`UC` 上传校验 480×360 JPEG 后复制入槽并
  记 CRC；旋钮换页/进入时 `show_cached()` 校验 CRC、终止旧页在途流（07）、复制到 RX 对齐源后解码并显示。区域帧
  上限降为 81920 字节。全部在 RAM，不写闪存。回归 `tests/test_cache_pipeline.py`（16 项）。构建 dev `04f09a6d…`、
  release `ba2224b7…`。

### 帧页号标签（两个版本）

BA 起始包第 8 字节（原为补零）= 1 + 主机页号；`rt_receive` 记入 `rt.frame_tag`，`display()` 校验后若非缓存上传且标签

### 旋钮接管（两个版本，flags bit 6）

用户 2026-11-09 要求两个旋钮的转动和按下都能自定义（原厂驱动和 Aula Hub 都不能改）。按下和音量旋钮本来就作为
媒体键到电脑（见上文“按下”），由电脑端键盘钩子接管；屏幕旋钮的转动只到屏幕芯片，所以固件加了接管：
`A5 3B 07 01` 后，`rt_key` 在武装期间对每次转动只发 `21 dir 01`（第三字节 01 = 已接管，普通转动仍是两字段的
`21 dir`），直接返回，不调用原 key/page，不碰槽位、主机分页或原厂页号，也就没有原厂 2 s 页面保存。
`A5 3B 07 00` 恢复原厂翻页。没有武装的会话时拒绝（EE）；LEAVE 和主机超时清零，所以主机挂掉 10 s 内旋钮自动
恢复翻页，新会话从不接管开始。接管期间 `A5 3B 30` 的电脑步进仍要翻页（服务的“屏幕下一页/上一页”动作）：
`rt_control` 给 `rt.pass` 加一（上限 8），`rt_key` 消耗一次后照常执行且不上报，主机不会把自己的步进当成
一次转动再映射。Runtime 末尾加 `takeover`、`pass` 两个 u32（`0x1110` 字节，仍在 `0x1200` 内）。HELLO flags
127。回归：`test_takeover_reports_turns_and_moves_no_page`（dev/release，槽位可见及停在原厂页两种情况，
配置页逐字节不变、零配置调用）、`test_takeover_lets_host_steps_through_unreported`、
`test_takeover_ends_with_the_session_and_needs_one`；集成 `test_sdk_knob_takeover_on_the_real_firmware`。
电脑端（`sdk/src/neos75screen/knobmap.py`）：只有屏幕旋钮的“按住转动”被设置时，按下（计算器键按下）才打开
接管，松开就关掉，平时转动照常翻页；转动本身被设置时整个会话接管。

### 配置保存链与三个失败的处理

【观察】原 key 写 current `0x200044AD`，再原 `0x3C128` 写 pending `0x200045D6`（u16）和
timestamp `0x200045D8`（u16）。`0x3D2FC` 取 tick 低 16 位；`0x3D18C` 计算环绕差。
原 `0x33FA4(0)` 满 2000 ms 后调用 `0x17A4C(0x0F,pending)` → 两次 `0x1788C` → `0x178B4`，
变更时才经原 flash 包装追加记录。key `0F/10` 始终保存原厂页号/临时标志，未保存 RT。

ENTER、进入槽位、LEAVE、可见超时仅加载 screen，不调用原编号切页，也不清除/重置先前用户的 pending。
实时可见时每轮调用原 `0x33FA4(0)`，让“用户先选 stock 页、两秒内又转回 RT”的待保存操作准时执行。
不传强制保存参数，不保存 key `11`；此前 `0x3379C` 的恢复窗口保护继续保留。
旋钮从 RT 选 stock 页会创建正常的原厂保存，这是用户选择原厂页产生的允许写入，不算虚拟槽位持久化。

真实机器码回归把原 `0x1D268` BL 恢复为对照，逐步比较未武装时正反各六次转动的 current、overlay、
pending、配置 RAM、当前 screen、完整配置页以及**全部保存链调用地址和参数**，要求完全一致。
武装回归在每个 stock 选择后断言 1999 ms 内没有页号保存、2000 ms 恰好一次 `17A4C(0F,页号)`；
进入槽位、帧显示、LEAVE 和超时的隔离窗口要求整个保存链调用为 0，而非只看最终 flash 字节相同。
正常静态页自己的 key13 调用保留并由未武装原厂对照核验，没有全局屏蔽保存。

本轮开始先复现 **3 个失败**，原因和修复如下，未削弱以上计数或原厂对照断言：

1. 正反循环两项测试每页等待 2 s，共超过 10 s，却未发送任何主机保活，固件按规范超时解除。
   测试改为每页选择前经真实控制入口发送 STATUS；旋钮仍不刷新租期，独立超时测试仍要求解除。
2. 门禁测试只写 BF77=0，fixture 的 context 实际为 0，误期望原厂一定禁止；测试现在明确构造非零 context
   测锁定，继续验证 overlay 只改 current 的原厂行为和不杜撰 press。
3. 同时发现固件原先把 `!BF77` 当作整个 page gate，漏了 context-null 例外。固件改为逐条件匹配原厂 gate，
   另加 native 回归验证 context=0、BF77=0 时仍能离开 RT，并保留 1999/2000 ms 的原保存时序断言。

native 模拟只新增 RTOS queue create/get/put 边界桩 `0x2F63C/0x2F560/0x2F680`；生产者、消费者、
GUI 回调、页面与配置逻辑不打桩。轻量 `Machine.inject_knob(dir)` 仅排入测试队列，`gui()` 消费；
`advance(ms)` 推进同一虚拟时钟。StockGUI 则通过真实 producer/read callback 执行；均不访问设备。
SDK 集成使用真实 SDK、白名单和上传器。`fake_device.py` 的 3 页、patch=2、重复 ENTER/LEAVE 无条件事件
只是 fixture 的简化解读（隐藏 LEAVE 保留当前页与固件一致）；固件遵循本节的 6 页、patch=3 和协议的可见性变化/入口恢复语义。
SDK 字段解析及 keepalive 与协议相容，现有测试和 SDK 源码未修改；新建 `tests/integration/test_knob.py`。

## 试运行标志、栈与执行上界

dev 的 init 表指向 rt_init，保留未确认标志；不会调用原 mcu_run_success。
release 同样跳过 init 清除，直到至少 6000 次 GUI 回调且首个回调起 uptime 差≥60000 ms，才调用
原 `0x2E010` 一次。该原函数只在标志匹配时按原路径擦 `0x7000` 页；补丁没有另写内部闪存地址。
【推断】持续执行 GUI 回调加上未复位的 uptime 可作为“稳定运行”的初步条件，不等同于全部外设健康证明。

【观察】GCC `.su` 记录每个新函数栈帧。HID 的 BA 路径最多 rt_ba 16 + enqueue 16 = 32 字节；
USB 控制路径 rt_usb 8 + enqueue 16 = 24 字节。没有 64 字节报告局部数组。
GUI 的格式校验新代码峰值为 rt_gui 32 + rt_validate 24 + rt_jpeg 120 = 176 字节；
这是补丁新增函数的帧合计，不含原 timer handler/RTOS/ISR。A5 控制回复的局部数组 32 字节，
rt_control 帧 48 字节；调用原 cache invalidate 额外可见序言为 24 + close 8 字节，decoder close 的深层帧另计。
新增 rt_status_save 栈帧为 0；为了在原轮询返回后清标志，rt_gui 在 stock_poll 期间保留自己的 32 字节帧，
不再像旧版本那样在尾跳前释放该帧。这 32 字节增加需纳入真实 GUI 栈水位回归，纯模拟不证明最坏峰值。
v3 的 rt_key 帧为 32 字节，enter/hide/leave 各 16，visibility_event/reply 各 16；这些只在 GUI 使用，
UART/HID 不增加页面、对象或解码调用。原厂 LVGL/页面创建深层栈不包含在这些数字中，仍需测 GUI 栈水位。
【推断】新 GUI 纯逻辑加原 JPEG 外层/校验调用链通常低于数百字节；原 LVGL 内部及 ISR 嵌套峰值
尚未实测，不能把 0x1000 GUI 栈的余量当成已经证明。

【观察】新增所有循环由 64、16、4096、480×360 或 172804 的固定上限约束；Huffman 重复符号检查
使用位图，避免平方复杂度。RGB 单次拷贝≤4096；JPEG 前移≤172791 字节；JPEG 原等待为 10 RTOS ticks，
超时执行原复位。一次回调最多解码一帧，未关调度器，未包围解码/校验关闭中断。
【推断】appdog 优先级 0x28 高于 HID 0x26 和 GUI 0x21，新增工作可被它抢占；不会靠 GUI 自行喂狗掩盖卡死。
【未知】CPU/外 RAM 实际耗时、10 ticks 的硬件时间以及原 LVGL/解析器全链路最坏时间，必须上机测量；
这里只给出数据/指令循环上限及等待参数，不冒充实测毫秒上界。
v2 图像缓存清除最多遍历原初始化的 1 项；不在 HID 调用。RGB 每回调最多搬 4096 字节；
在输入上限内 RGB 像素字节数≤172792（按 8 字节对齐的上界），需要至多 43 个拷贝回调，期间 image 隐藏。
JPEG 每帧仅一次校验、一次有界前移和一次原同步等待；整屏像素数比 v1 上限增加 68.75%，
10 ticks 超时策略未放宽，是否足够须由下一阶段测量。小帧采用居中对象，没有新增整屏 memset 或逐行搬运。

## 刷写工具及离线验证

`tools/flash.py` 独立实现通用工具，沿用原恢复脚本的 DFU 传输、描述符和默认 alt=0 约束，
不导入该恢复脚本或 HID 工具。`--image` 校验向量、大小，按实际覆盖扇区 FF 补齐；`--restore`
额外核验原备份摘要，写满其覆盖的 119 个 app 扇区。拒绝 `<0x8000`、配置页、外闪及不在镜像
覆盖范围的擦除。DATA 必须紧跟该扇区的擦除/设址，且逐字节等于规划镜像；不能随意指定数据。

所有显式控制传输先过 Gate，再到后端。设备必须已经在 DFU，且 VID/PID、产品名、两个 alt、

### 保留的 BA 长度语义修正与独立核对

此前接收器及其测试分包器错误地把块末 CRC 算入 `n`，导致 SDK 跨块上传收不到 ACK；该错误已修正。
依据负责人提供、曾在真机成功使用的 `screen_upload.py:65–86`：
`frame([n, *stream[pos:pos+n], *(crc if last else b'')])`，`n=min(62,end-pos)`。
该次修正只读了参考脚本，没有导入或执行其中的设备代码。回归用独立的整块/尾块分包规则生成
完整 64 字节报告，与修正后的 `packets()` 逐字节比较，再经 HID→GUI→接收/拷图机器码验证。
覆盖 dev/release、多块数据、CRC 位置、精确 ACK 时机、缓冲内容及最终图像。

【观察】额外在 Unicorn 中执行原备份的 `0x34FC8` ACK 构造器及 `0x104DC` 校验代码，
仅对内存拷贝/清零、发送作桩；新旧完整 64 字节 ACK 一致。格式如下，末尾补 55 个零：

| 类型 | 首包 ACK（前 9 字节） | 块 ACK（前 9 字节） |
|---|---|---|
| `5A` | `BA 07 A5 5A 00 02 FE 01 A4` | `BA 07 A5 5A 00 02 FE 00 A5` |
| `5B` | `BA 07 A5 5B 00 02 FE 01 A3` | `BA 07 A5 5B 00 02 FE 00 A4` |

校验字节为 `~sum(type,00,02,FE,first) & 0xFF`，不含 `BA 07 A5`；首包 payload 为 `FE 01`，
块 ACK 为 `FE 00`。格式无需修改。按 PROTOCOL，对每个完整块发 ACK，包括恰好结束整流的完整块。

【观察】原备份 `0x31E6C→0x31A6C` 在已接收块中间可接受短包；离线原机器码对照覆盖
`n=1/7/31/61`，新接收器回归覆盖中间所有 `n=1..61` 以及分片短尾。原厂例程对照只运行纯接收、
进度运算与内存拷贝路径，未进入外闪写或外设。CRC 错误、旧错误长度语义及报告容不下 CRC 的
输入均有拒绝测试。v3 保留 BA 长度/CRC/ACK 语义；`A5 3B`、BA `5A/5B` 不变，proto_version 按既定旋钮规格升级为 2。
